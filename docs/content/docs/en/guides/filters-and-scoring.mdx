---
title: Filters and Result Interpretation
description: Combine area, paper type, spotlight, search depth, and minimum score correctly.
---

Filters express explicit constraints; they do not replace the query. Search first, then call `list_paper_areas` to discover valid values.

## Filters

| Parameter | Use it when | Important detail |
|---|---|---|
| `area` | The research area is known | Use an exact corpus value |
| `paper_type` | The paper category matters | Values come from the current snapshot |
| `spotlight_only` | Only spotlight papers are wanted | The candidate pool may shrink sharply |
| `min_score` | The rank tail should be removed | Use only as a coarse per-query filter |

Dense and BM25 apply identical filters during retrieval. `min_score` applies after fusion.

## `top_k` and `search_depth`

`top_k` limits the number of new papers returned. `search_depth` sets the fused candidate window. Seen papers are removed only from that window, so the parameters solve different problems.

```text
top_k=5, search_depth=20
20 candidates -> remove session seen -> return at most 5
```

Increasing depth adds local retrieval and deduplication work but does not create multiple query embeddings. Do not set it to the global maximum by default; inspect `truncated` and empty-round guidance first.

## Correct use of `min_score`

Weighted RRF score encodes positions in the two rank lists. Appropriate uses are ordering one query's results, removing clearly trailing candidates with a conservative threshold, and deciding whether to adjust the current window.

Do not interpret `0.8` as an 80% relevance probability, compare fixed thresholds across queries, or treat score as paper quality, acceptance level, or citation impact.

## Debugging filters

When results are unexpectedly empty, remove `min_score`, spotlight, paper type, and area in that order, then check whether the session has already seen the candidates. If needed, run the same query without a session to separate retrieval behavior from deduplication.
