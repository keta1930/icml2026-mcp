---
title: 容量与并发
description: 评估 25–40 名间歇用户的默认边界，并安全调节本地与 provider 并发。
---

默认配置服务约 25–40 名间歇调用者。它不是 40 个持续占满的并行 search worker；匿名请求通过限流、admission 和分层 semaphore 收敛。

## 默认边界

| 项目 | 默认值 |
|---|---:|
| 每 IP 搜索速率 | 6 次/分钟，突发 3 |
| 每 IP 每 UTC 日 | 200 次搜索 |
| 每 IP 创建 session | 3 次/分钟，突发 2，每日 20 |
| 全局搜索速率 | 120 次/分钟 |
| active + waiting | 64 |
| 已 admission 等待 | 10 秒 |
| DashScope 并发 | 4 |
| Chroma 并发 | 2 |
| 在线日/月 Token | 500,000 / 10,000,000 |
| 活跃 session | 256 |

## 三类瓶颈

1. **Provider**：网络延迟、账户速率和 Token 额度。
2. **本地检索**：Chroma 线程安全、CPU、内存和磁盘延迟。
3. **State**：SQLite 写竞争、session 容量和 WAL 磁盘。

相同 query 的并发 cache miss 会 single-flight 合并为一次 provider 调用，因此命中率会显著改变实际容量。

## 调优顺序

先观察 provider latency、本地 search latency、队列等待、`server_busy`、cache hit 和 SQLite busy，再只调整对应边界：

- Provider 空闲而队列高：小步增加 provider concurrency。
- Chroma 延迟快速上升：保持或降低 Chroma concurrency。
- SQLite busy：缩短事务或降低并行状态写，不先增加 timeout 掩盖问题。
- 公共费用高：降低 IP/global rate 或 Token budget，提高 cache TTL。
- Session 容量高：缩短 TTL 或要求客户端及时 close，不随机淘汰活跃会话。

每次只改变一组参数，并重新运行混合并发测试。不要用多个应用 worker 共享 Chroma 目录扩容。

## 磁盘规划

Canonical index 与 runtime copy 会同时存在。发布新 generation 时还会短暂保留旧 runtime，因此生产 state 空间至少按两个 runtime index 加 SQLite/WAL 与文件系统余量规划。
